## Context

The `TraceabilityGraph` stores relationships as directed edges keyed by `fromId-type-targetId`. When a user writes complementary relationships from both sides (e.g., `leads_to:REQ-001[]` in UC-003 and `is_derived_from:UC-003[]` in REQ-001), the graph stores two separate directed edges. The `inverseLabels` config already maps `leads_to → is_derived_from` for display purposes in `incoming[]` macros, but this mapping is not used at relationship-storage time.

The `autoGenerated` flag on `ItemRelationship` exists but is only set to `false` for invalid relations. The `inverseOf` field exists but is never populated. The `_inverseIndex` member is declared but never used (only cleared in `clear()`).

## Goals / Non-Goals

**Goals:**
- Detect that two user-authored relationships form a complementary pair (type A→B and invType B→A) and store them as one
- Mark the merged relationship so downstream code (validation, visualization, export) can handle it correctly
- Prevent false circular-reference warnings from bidirectional pairs
- Remove dead code (`_inverseIndex`)

**Non-Goals:**
- Auto-generating inverse relationships from single-sided declarations (that's a separate feature)
- Changing the `inverseLabels` config format
- Modifying `DocumentParser` — it only extracts inline macros, doesn't participate in merging

## Decisions

### Decision 1: First-writer-wins merge strategy

When an inverse pair is detected, the first relationship stored remains as the canonical entry. The second (inverse) call to `addRelationship` is silently dropped — no warning. The surviving relationship gets `bidirectional: true`.

**Alternatives considered:**
- *Warn on merge* — noise for intentional usage. The user deliberately wrote both directions; warning them is unhelpful.
- *Keep the second, drop the first* — breaks sourceFile/line metadata pointing to the first file processed. First-writer preserves the earliest context.
- *Merge metadata (e.g., `sourceFiles: [file1, file2]`)* — complex, no clear consumer.

### Decision 2: Inverse type resolution order

Look up the inverse type from (in priority order):
1. `config.inverseLabels[type]` — user-configured mapping
2. `INVERSE_MAP[type]` — compile-time legacy mapping (types.ts)

If neither exists, the relationship type has no inverse — store as a regular directed edge.

### Decision 3: Bidirectional flag, not autoGenerated

The merge marks the surviving relationship `bidirectional: true`, not `autoGenerated: true`. Reason: `autoGenerated` edges are skipped by `findCircularReferences`. Bidirectional pairs would be skipped too, but they should be — A→B and B→A with complementary types is not a cycle. Using a separate flag lets us distinguish "this is an auto-generated convenience edge" from "this is a user-authored bidirectional pair."

### Decision 4: Remove `_inverseIndex`

Dead code. Declared at class level, never populated, only cleared. One less thing to maintain.

## Risks / Trade-offs

- **Asymmetric deletion**: If the user removes one side's inline macro and rebuilds, the surviving side becomes a regular directed edge again. This is correct behavior — the remaining macro is still a valid declaration → covered by existing behavior.

- **No merge undo**: Once merged, the inverse's metadata (sourceFile/line) is lost. If the user wants to preserve both source locations, they shouldn't use bidirectional pairs → acceptable trade-off; the alternative (array metadata) is complexity with no consumer.

- **Config dependency**: If `inverseLabels` is misconfigured (missing an inverse mapping for a type that users write both directions of), duplicates won't be merged. Not a bug — the config is the source of truth → documentation note.
