## Context

Antora classifies pages and partials separately.
A partial contributes its content to an including page but is not published as a navigable page.

The traceability graph already records `component`, `module`, `version`, and the partial `sourceFile` for UC-007.
The missing fact is the rendered page that includes the partial.

AsciiDoc relationship links are generated by `AntoraTraceabilityExtension.buildXref`.
Generated matrix and attachment links are generated later by `LinkResolver`.
These paths currently resolve partial source files independently, so they can produce a same-page anchor or a file URL.

## Goals / Non-Goals

**Goals:**

- Resolve partial-defined items to the page that includes their partial.
- Use the same resolved target for AsciiDoc xrefs and generated matrix/attachment links.
- Preserve partial source provenance in the graph.
- Use existing `component`, `module`, and `version` metadata for Antora qualification.
- Target explicit item IDs such as `#UC-007`.
- Keep CLI behavior unchanged when no Antora include context exists.

**Non-Goals:**

- Do not publish partials as standalone pages.
- Do not replace explicit item anchors with generated heading anchors.
- Do not add configuration for partial link resolution.
- Do not add dependencies or change the traceability graph's node identity.

## Decisions

### Maintain a shared partial-target index in the Antora extension

During `contentClassified`, scan AsciiDoc page contents for `include::partial$...[]` directives.
Index each partial by component, version, module, and normalized partial path.
Store the including page's normalized source path and published URL when available.

The index belongs to the Antora extension because include relationships are content-catalog knowledge, not intrinsic graph-node data.
The graph continues to preserve the source partial and existing component/module/version fields.

### Resolve links through the index before source-file fallback

`buildXref` receives the current component/module context and uses the partial-target index to emit a qualified xref such as:

```text
xref:tracer:ROOT:self-traceability/use-cases#UC-007[UC-007]
```

If no include target is known, retain the existing fallback behavior rather than inventing a page.
This preserves CLI and unusual content-catalog scenarios.

`LinkResolver` receives the same target index or a resolved target callback.
For a partial item, it generates the target page URL from the including page's published URL and appends `#<item.id>`.
This produces the rendered URL:

```text
/tracer/stable/self-traceability/use-cases.html#UC-007
```

### Keep target resolution separate from item provenance

Do not overwrite `Item.sourceFile` with the including page.
Source provenance is used by graph diagnostics, exports, and source inspection.
The rendered target is derived only at link-generation time.

### Handle duplicate includes deterministically

If one partial is included by multiple pages in the same component/version/module, retain all targets in the index.
When a link has no page-specific context, select the first catalog page in stable catalog order and emit a warning for ambiguous targets.
Future callers with page context may select the matching target without changing graph identity.

## Risks / Trade-offs

- A partial included by multiple pages cannot have one universally correct destination for a link generated outside a page context.
  Keeping all targets avoids losing information; deterministic fallback prevents broken links.
- Include syntax other than `include::partial$...[]` may not be discovered by the first implementation.
  Existing Antora partial syntax is the supported scope; unresolved forms retain the safe fallback.
- Generated matrix links use published URLs while AsciiDoc links use Antora xrefs.
  Both are intentionally derived from the same target record but remain format-specific.
