## Context

Item blocks render through the standard Asciidoctor HTML5 converter, which emits only `id`, `class`, and `style` on the block element. AsciiDoc block attributes other than the role shorthand and `id` do not reach the HTML: verified against the installed converter, `[#R1,item,role=requirement,data-status=draft]` renders `<div id="R1" class="openblock requirement">`, and both a tree processor setting the attribute and an inline anchor carrying it are equally discarded. Emitting `data-*` therefore requires either an HTML post-processing pass or a converter subclass.

Two constraints shape the approach. The project's own requirement CON-003 records that all content generated by the extension's macros SHALL use standard AsciiDoc constructs only, not raw HTML, so that all backends including PDF remain supported. And the PDF build is a shipped deliverable (`ci-pdf-deploy`), so an HTML-only mechanism makes the decoration HTML-only by construction.

Item header recognition is currently hardcoded to the `tracer` role at six sites, so a hand-written or newly emitted role class in the header is not recognized as an item.

## Goals / Non-Goals

**Goals**

- A stylesheet-only path from item metadata to rendered decoration, requiring no per-item authoring.
- Recognition of arbitrary role-class prefixes in item headers, so emitting a class cannot break parsing.

**Non-Goals**

- Any decoration in the PDF or DOCX builds. The emitted class is HTML/CSS-only; PDF keeps today's output.
- Decoration for items inside generated relationship lists, which are built as xref strings separately from item blocks.
- A configuration option to control emission; the stylesheet is the switch (see Decisions).

## Decisions

### Emit a CSS class rather than `data-*`

`role=` is already a CSS class in the rendered output, needs no converter work, and is backend-neutral. `data-*` cannot be emitted without either post-processing generated HTML (violating CON-003, and unusable from PDF) or subclassing the Opal-based converter. Since the decoration is presentational, a class carries everything required and the site stylesheet supplies the icon.

Alternative rejected: a `pagesComposed` pass rewriting `page.contents` HTML. It reaches `data-*` but is HTML-only, parses generated HTML, and has no PDF story.

### Class is emitted unconditionally; the stylesheet is the opt-in

An unstyled class renders nothing, so "always emit" has no visible cost. A configuration switch would buy only a tidier DOM while costing document-attribute plumbing into the substitution pass plus a partial-handling rule, since partials carry no attributes of their own. Per-page control is already available: the UI layout puts `page.attributes.role` on `<body>`, so a page header `:page-role: show-status-icons` scopes stylesheet rules to that page.

Alternative rejected: a `traceability-status-classes` attribute following `isLinksEnabled`/`isGraphEnabled`. Reconsider only if the unrequested class becomes a problem in third-party stylesheets.

### Namespace: `tracer-status-<slug>`

The matrix already emits `status-done`, `status-partial`, and `status-missing` for coverage (`src/templates/partials/matrix-row.mustache`, styled in `styles.mustache`). A bare `status-` prefix for item metadata would collide semantically: an item with `status=done` would produce a class identical to a matrix coverage class, and a global rule would bleed across both. The `tracer-` namespace also matches existing naming (`tracer:` macro alias, `tracer-role` docs).

### Slug rule

`status` is free-form; the parser only strips quotes. Rule: lowercase, replace each run of non-alphanumeric characters with a single `-`, trim leading and trailing `-`. Verified: `In Review` → `in-review`, `2.1` → `2-1`, `open/closed` → `open-closed`, `DRAFT` → `draft`, `""` → empty. The `tracer-status-` prefix also neutralizes digit-leading values, so no separate guard is needed. Empty slug emits no class.

Alternative rejected: preserving the raw value. `status="In Review"` would put a space inside the class attribute.

### Injection point: the existing title-injection pass

`injectTitleIds` already walks every item header with a quote-aware scan and already holds the graph. Extending it keeps one header-rewrite pass instead of adding a second. Injection is idempotent (skip when the class is already present), so a hand-written class is left alone.

### Generalize header recognition at all six sites

Replace the `(?:\.tracer)?#` group with `(?:\.[A-Za-z0-9_-]+)*#` at: `src/DocumentParser.ts:158`, `src/antora-extension.ts:457/1967/2026/2448`, `src/cli.ts:266`. Verified: this recognizes the plain, `.tracer`, `.tracer.status-draft`, and multi-class forms without changing existing matches.

### Decoration ships in the UI theme, not only as site CSS

The class emitting the value is meaningless to a reader without a rule that draws it, and the extension cannot ship CSS. `antora-ui-conemso` is the theme these sites use and already carries one Tracer-aware rule (`.doc .openblock.tracer > .title`), so it is the right owner for default badges. Five common statuses get a `::after` label; any other value is left to the project's stylesheet, keeping the theme from inventing vocabulary the extension does not define.

Consequences: the extension's playbook pins move to the new theme release, and a project on a different theme still gets the class but no badge — which is the documented behavior.

Alternative rejected: shipping a stylesheet with the npm package. It would not be loaded by Antora (the UI bundle owns styles in a rendered site) and would duplicate what the theme already does.

## Risks / Trade-offs

- **`stripSupersededBlocks` (`antora-extension.ts:2448`) only matched the old `.tracer` form** → superseded items written with a status class would stay visible. The regex generalization is a required part of this change, not a tidiness fix; cover it with a test.
- **`2448` requires a trailing comma after `item`** (pre-existing). Headers with a status class and no following attribute are not matched by that pattern. Out of scope here; note it so the next reader does not attribute it to this change.
- **The example site cannot demonstrate the feature** — exactly one of 408 items declares a status (`REQ-355`, `status=draft`). Use that item for the documented stylesheet example rather than editing many items.
- **Theme badges couple the UI repo to a status vocabulary.** The theme names five statuses the extension does not define. A project using different words gets no badge until it adds a rule → mitigated by styling only widely-used values and documenting that unlisted values render nothing; the theme changelog records the list.
- **The CI playbook (`antora-playbook-ci.yml`) still pins an older theme (`v1.1.3`)** and therefore has no badges. Deliberate: that playbook publishes multiple versions and was last bumped separately → leave the pin alone; the main playbook carries the new theme.
- **A class is not a localization mechanism.** The icon comes from one stylesheet rule per value; a second language or a new status value needs its own rule. Acceptable because the same is true of any CSS-driven decoration, and CON-003 rules out the value-driven alternative.
- **Any role class in a header now becomes an item header** → a page using a coincidentally item-shaped pattern with a role class could newly parse as an item. Mitigated by the existing requirement that the header contain `, item`; verbatim ranges remain excluded.

## Migration Plan

Additive and off by default at the visibility level: unstyled classes change no rendered appearance. No configuration or source migration. Rollback is removing the injection; hand-written classes would then stop being recognized, which is a strict regression from the current parser behavior only for headers that were already ignored.

## Open Questions

None blocking. Deferred by the proposal's non-goals: icons in generated relationship lists, and any PDF decoration.
