## Context

`query` currently builds a local graph from `.adoc` files and supports `reverse`, bidirectional `impact`, `isolated`, `orphaned`, and `path`. `TraceabilityGraph.getImpactAnalysis()` is not suitable for this query: it follows both incoming and outgoing edges. `site-graph <playbook> --out <path>` already harvests all Antora content sources and serializes a canonical graph snapshot.

## Goals / Non-Goals

**Goals:**

- Query forward-reachable items filtered by role, across arbitrary path lengths.
- Use the existing local-file query path for one repository and existing site-graph snapshots for multi-repository queries.
- Return each matching item once, with optional JSON output consistent with current query commands.
- Document globally unique IDs as a prerequisite for an unambiguous complete graph.

**Non-Goals:**

- Changing `impact` semantics or existing query behavior.
- Resolving duplicate IDs by component-qualified identity or adding duplicate-ID enforcement in this feature.
- Making a query command harvest the Antora playbook on every invocation; users generate a snapshot with the existing `site-graph` command and query that artifact.
- Filtering by relationship type or returning traversal paths; the requested result is the set of reachable items for one role.

## Decisions

### 1. Add a separate forward-only `linked` query

Use `query linked <id> <role>` instead of changing `impact`. Traverse outgoing graph relationships only. Add each visited item ID once and continue traversal regardless of role; collect only items whose role matches the requested role. Do not include the starting ID, even if it matches the role. This supports paths through intermediate roles and terminates on cycles without a depth limit.

### 2. Reuse the graph sources already supported

For a local query, retain the existing `--input <path>` behavior. Add `--snapshot <path>` for a snapshot generated by `site-graph`; restore its items and relationships into the query graph and run the same linked query. Treat an explicitly supplied `--input` and `--snapshot` as mutually exclusive; when neither is supplied, preserve local scanning of the current directory. Do not add direct playbook harvesting to `query` or another snapshot format.

### 3. Require globally unique IDs for complete graphs

The current graph and relationship APIs address items by bare ID. Do not imply that duplicate IDs from separate repositories are safely distinguished. Document global uniqueness as a prerequisite for multi-source queries and recommend `@antora-tracer/id-server` seeded from the playbook, with shared allocation settings that preserve uniqueness across all included repositories. Duplicate detection or component-qualified graph identity is a separate change.

### 4. Keep output conventional

The default table contains ID, Role, and Title, matching `query impact`; `--json` returns full matching `Item` objects. Empty results exit successfully. Unknown starting IDs and incompatible source options report errors and exit non-zero.

## Risks / Trade-offs

- Snapshots can become stale after content changes; users must regenerate them with `site-graph` to query the current playbook graph.
- ID uniqueness is a documented prerequisite, not enforced by this feature. Duplicate IDs can make a multi-source lookup ambiguous.
- Outgoing direction follows the canonical graph edge direction, which may differ from the direction in which an inverse relationship macro was authored.
