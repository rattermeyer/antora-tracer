== Validation and Maintenance

=== UC-007: Developer validates traceability in CI pipeline

[#UC-007, item, role=use_case, title="Developer validates traceability in CI pipeline"]
--
[width=100%, cols="25h,75a"]
|===
| ID | UC-007
| Title | Developer validates traceability in CI pipeline
| Goal | Developer runs traceability validation in CI so that invalid relationships, circular references, and configuration errors are caught before they reach the published site
| Primary Actor | Developer or DevOps Engineer
| Preconditions | The Antora Tracer CLI is installed in the CI environment And the project's `.adoc` source files are checked out And a `traceability.yml` config is present And the CI pipeline has a step for traceability validation
| Trigger | A pull request is opened or a commit is pushed — the CI pipeline triggers a traceability validation job
| Basic Flow |
. CI pipeline checks out the repository
. CI pipeline runs `antora-tracer process -i <pages-dir> --config traceability.yml` to parse all items
. CI pipeline runs `antora-tracer validate -i <pages-dir> --config traceability.yml` to check graph integrity
. The validator reports errors (circular references, invalid relations) and warnings (unknown roles, missing targets)
. If errors are found, the CI pipeline fails the build and the developer reviews the output
. Developer fixes the issues — removes circular references, corrects relation types, or adds missing targets
. Developer pushes the fix And CI re-runs validation
. When validation passes (0 errors), the pipeline proceeds to build and deploy the Antora site
| Alternate Flows |
. *Validation finds only warnings (no errors):* The build continues. Warnings are logged for review but do not block deployment.
. *Circular reference detected (e.g., A → B → A):* The validator reports the full cycle path. Developer must break the cycle by removing one of the relationships.
. *Config file is missing or invalid:* The validator exits with an error describing the config problem. Developer fixes `traceability.yml`.
. *No items found in the input directory:* The validator reports 0 items. This may be intentional (new project) or indicate a path misconfiguration.
. *Developer wants to run validation locally before pushing:* Same commands work outside CI — `process` then `validate`.
| Postconditions | The traceability graph is free of structural errors (0 circular references, 0 invalid relations) And the CI pipeline has verified the config is valid And the build can proceed to site generation
| Priority | High
| Frequency | On every push or pull request — continuous integration
| Notes | The `process` step must run before `validate` — validation operates on the in-memory graph populated by processing. In the example site, matrices are generated by the extension at build time; the CLI's `matrix` and `export neo4j` commands remain available for standalone or CI artifact generation.
|===

=== UC-010: Developer assesses impact before changing a traceable item

[#UC-010, item, role=use_case, title="Developer assesses impact before changing a traceable item"]
--
[width=100%, cols="25h,75a"]
|===
| ID | UC-010
| Title | Developer assesses impact before changing a traceable item
| Goal | Developer queries the traceability graph so they can identify every item that references a target before changing or removing it, avoiding dangling references and broken coverage
| Primary Actor | Developer or Requirements Engineer
| Preconditions | The project's `.adoc` source files contain traceable items with IDs And the Antora Tracer CLI is available And the developer has read access to the source files
| Trigger | Developer plans to change, rename, or remove a traceable item and needs to know what references it
| Basic Flow |
. Developer identifies the ID of the item they intend to change or remove
. Developer runs `antora-tracer query reverse <ID>` to list every item that references the target, with relationship type and source file and line
. Developer runs `antora-tracer query impact <ID>` to list all items transitively connected to the target
. Developer reviews the results to determine the full set of items affected by the change
. Developer updates each referencing item — or confirms none exist — before making the change
. Developer commits the change with all affected items accounted for
| Alternate Flows |
. *No item references the target:* `reverse` returns an empty result and exits 0. The change is safe from a traceability perspective.
. *The target ID does not exist:* The command exits 1 with an "Item not found" warning. Developer verifies the ID spelling or confirms the item was already removed.
. *Developer needs machine-readable output:* Developer adds `--json` for structured output consumable by scripts or AI coding agents.
. *Developer needs the chain between two specific items:* Developer runs `query path <from> <to>`. The shortest relationship path prints, or the command exits 1 with "No path found".
. *Developer wants to find items with no relationships:* Developer runs `query isolated`, optionally filtered with `--role`.
. *Developer wants to limit the search:* Developer passes `-i <path>` to scan a specific directory or file instead of the current directory.
| Postconditions | The developer has identified every item that references the target And no Antora build was required And no source files were modified (query is read-only) And the change can proceed with all referencing items accounted for
| Priority | Medium
| Frequency | Before each refactor, rename, or removal of a traceable item
| Notes | The `query` command parses `.adoc` files directly — it reuses the same parser and graph as the build, so no Antora build or running Neo4j database is required. This is the lightweight in-repo counterpart to UC-008 (Neo4j exploration): `query` answers simple structural questions without infrastructure, while Neo4j supports deeper ad-hoc graph analysis. ⚠ Actor "Developer or Requirements Engineer" is a compound role without a persona definition.
|===

=== UC-013: Requirements Engineer retires an obsolete traceable item

[#UC-013, item, role=use_case, title="Requirements Engineer retires an obsolete traceable item"]
--
[width=100%, cols="25h,75a"]
|===
| ID | UC-013
| Title | Requirements Engineer retires an obsolete traceable item
| Goal | Requirements Engineer marks an obsolete item as superseded And cleans it out of the active set so that current-state views reflect the successor while the item's history is preserved
| Primary Actor | Requirements Engineer, Developer, or Tech Lead
| Preconditions | An obsolete traceable item exists in the graph And (a replacement successor has been authored Or the item is isolated with no relationships) And the Antora Tracer CLI is available And the Requirements Engineer has write access to the source `.adoc` files
| Trigger | Requirements Engineer determines that an existing item is obsolete and must be replaced or removed
| Basic Flow |
. Requirements Engineer marks the successor as replacing the obsolete predecessor
. Requirements Engineer runs the supersession check for the predecessor to list direct successors And incoming functional relationships requiring review
. Requirements Engineer runs validation to confirm the supersession structure is valid — no self-reference, duplicate, or cycle — And to review stale functional-link warnings
. The build renders the superseded item with a marker linking to every direct successor And current-state matrices omit the superseded item
. Requirements Engineer reviews functional relationships that still target the obsolete item And updates them to the successor
. When cleanup is due, Requirements Engineer archives the superseded item out of the active pages or removes an orphaned or isolated item after confirmation
| Alternate Flows |
. *Supersession structure is invalid (self-reference, duplicate, or cycle):* Validation reports an error And the Requirements Engineer fixes the relationship.
. *A functional link still targets the superseded item:* The link is retained And flagged as requiring review, naming every direct successor; validation warns without failing.
. *A dangling link of type `supersedes` or `superseded_by`:* Reported as an advisory worklist item, not a validation error.
. *Hide superseded items from rendered output:* The Requirements Engineer disables rendering of superseded items; the graph And matrices are unaffected.
. *Item is not superseded:* The archive command refuses to move it.
. *Item is isolated (no relationships at all):* Removal requires typing the item ID verbatim as a stronger confirmation.
| Postconditions | The successor is registered as replacing the predecessor And the obsolete item is marked superseded And current-state matrices And views show only active items And the obsolete item's history is preserved via successor links And the archive or remove command has confirmed the target item before mutating the file
| Priority | High
| Frequency | Whenever an item is replaced — during refactoring or requirement changes
| Notes | The `supersedes` relation And the archive destination page are defined by the requirements this use case traces to. Covers the supersession overview as an optional reporting aid. Actor "Requirements Engineer" does not yet have a persona definition. The supersession check is read-only; only the archive And remove commands mutate source files.
|===

=== UC-014: Developer compares traceability across two versions

[#UC-014, item, role=use_case, title="Developer compares traceability across two versions"]
--
[width=100%, cols="25h,75a"]
|===
| ID | UC-014
| Title | Developer compares traceability across two versions
| Goal | Developer diffs two sets of AsciiDoc sources so that they can see exactly which items and relationships changed between versions before merging or auditing
| Primary Actor | Developer or Requirements Engineer
| Preconditions | Two source paths (for example, a base branch and a revision) are available locally And the Antora Tracer CLI is installed And the Developer has read access to both source paths
| Trigger | Developer prepares to merge, release, or audit a change And runs the diff command
| Basic Flow |
. Developer identifies the two source paths to compare — the base and the revision
. Developer runs the diff command with both paths
. The CLI prints the delta between the two graphs
. Developer reviews items classified as added, removed, or modified by stable ID, with modified items naming the changed fields
. Developer reviews relationship changes limited to items that survive in both snapshots
. Developer uses the delta to plan the merge or document the change
| Alternate Flows |
. *An item was renamed without a supersedes relationship:* The diff performs no rename detection — the old ID appears as removed And the new ID as added.
. *A superseded item:* Its predecessor appears as removed And its successor as added, with the supersession relationship reported as a new relationship.
. *A relationship touches an item present in only one snapshot:* The relationship delta is not reported.
. *The two snapshots are identical:* An empty delta is printed And the command exits successfully.
| Postconditions | The delta — added, removed, and modified items plus relationship changes — has been printed And no source file has been modified
| Priority | Medium
| Frequency | Before merges, during release reviews, or when auditing traceability drift
| Notes | The diff is read-only And config-agnostic — it works with any role or relation vocabulary. No persona defined for the actor roles.
|===
